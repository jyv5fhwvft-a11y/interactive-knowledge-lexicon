OPERATING SYSTEMS | CONCEPT 002

Process

A Program in Execution

What happens when a computer actually runs a program?

A process is a program that is currently executing on a computer.

When you open an application, the operating system creates and manages a process so that the program can use the computer's resources, such as the CPU and memory.

1. Concept Identity and Definition

Concept ID: IKL-OS-002

Concept: Process

Subject: Operating Systems

Topic: Process Management

What Is a Process?

A process is an instance of a program that has been started and is being managed by an operating system. It has its own execution context, address space, one or more threads, and associated resources and management information.

In Simple Words

A program contains instructions. A process is an instance of that program being managed while it executes or waits to continue execution.

Program vs Process: What Is the Difference?

Program

A program is a passive set of instructions stored in a file.

  • Exists as stored code
  • Does not execute by itself
  • Waits to be started

Process

A process is an active instance of a program managed by the operating system.

  • Has an execution context
  • Uses memory and other resources
  • Can execute or wait

How Does a Program Become a Process?

What Does a Process Include?

A process is more than just the program's instructions. The operating system must keep track of several elements so that execution can be managed correctly.

  • Address space: The memory space associated with the process.
  • Threads: One or more execution paths within the process.
  • Execution context: Information needed to pause and resume execution, such as processor register values.
  • Resources: Resources associated with the process, such as open files and other operating-system objects.
  • Management information: Information the operating system maintains about the process, including its identity and state.

Important: Process vs Thread

A process provides the environment and resources in which its threads operate. The CPU schedules and executes threads, rather than treating the process as one indivisible execution unit.

Can One Program Have Multiple Processes?

Yes. A program can be started more than once, creating multiple process instances. Each instance is managed separately by the operating system.

Why Does the Operating System Manage Processes?

Several programs may need the computer's CPU, memory, storage and input/output devices at the same time. The operating system coordinates their use.

Understanding Process Isolation

Processes are given controlled memory and resource access so that one process cannot freely interfere with another. Isolation is not absolute: processes can communicate and share selected resources through operating-system mechanisms.

  • Explain how one program can have multiple instances.

3.4 The Real Operating-System Concepts

The restaurant analogy helps us understand the general idea. Now let's connect it to the actual computer concepts.

  • Program: A stored set of instructions that describes what a computer should do.
  • Process: An executing instance of a program that the operating system manages.
  • Operating system: System software that manages processes and coordinates access to computer resources.
  • CPU: The processor that executes instructions belonging to running threads.
  • Memory: Holds the instructions, data and other information needed during execution.
  • Process scheduling: The operating system's method of deciding which ready thread should receive CPU time.
  • Ready: A process has work that can proceed. More precisely, its runnable thread is waiting for CPU time.
  • Waiting / Blocked: A thread belonging to a process is waiting for an event or operation, such as input/output, to finish.
  • Termination: The process has finished its execution and is being or has been cleaned up.

Important: Ready and Waiting Are Different

Imagine two restaurant orders.

Order A: All ingredients are available, but the cooking station is busy. The order is ready for preparation.

Order B: The order cannot continue because a required ingredient has not arrived.

In a computer:

  • Ready: Waiting for CPU time.
  • Waiting / Blocked: Waiting for an event or operation.

These are two different reasons why a process may not currently be executing.

Important: The Process Is Not the CPU

In the restaurant analogy, the order represents the process. The chef and cooking station represent the ability to carry out the work.

In a computer, a process is the managed environment containing one or more threads. The CPU executes instructions belonging to those threads.

A process does not need to use the CPU continuously. It may receive CPU time, pause while another thread runs, or wait for an event such as a file operation.

The detailed process states and scheduling mechanisms will be explained in later sections.

Important: An Analogy Is Not the Actual Mechanism

A restaurant kitchen helps us imagine how work is organised, but a computer does not operate exactly like a restaurant.

A chef is a person who performs physical work. A CPU is an electronic processor that executes machine instructions.

The operating system uses scheduling algorithms, data structures, memory management and hardware mechanisms. It does not manage processes by behaving like a human manager.

Use the analogy to understand the relationships, not to assume that every restaurant activity has an exact technical equivalent.

4. Beginner Explanation

4.1 What Actually Happens When You Open an Application?

Imagine tapping the Calculator application on your computer or tablet. You expect the Calculator window to appear and allow you to perform calculations.

Behind that simple action, the operating system performs several jobs. It starts the application, establishes an environment in which it can operate, manages its resources, and coordinates its execution.

The operating system represents a running instance of the application as a process.

The Important Idea

Opening an application is not simply displaying a window. It involves creating or activating the work environment that allows the application to operate.

4.2 How Does the Operating System Create a Process?

Let's follow a simplified example of what can happen when you request an application to open.

  1. You request an application.

    You tap or click an application icon, such as Calculator.

  2. The operating system receives the request.

    The operating system handles the request and begins the appropriate application-starting procedure.

  3. The operating system prepares the process.

    It establishes an execution environment, creates the necessary management information, and arranges the memory and resources needed by the application.

  4. The process becomes ready to execute.

    Its runnable thread can enter the Ready state and wait for an opportunity to receive CPU time.

  5. A thread receives CPU time.

    The scheduler selects a runnable thread. The CPU can then execute the instructions belonging to that thread.

A Small Technical Detail

This is a simplified learning sequence. Actual application-starting procedures differ between operating systems. Some applications may reuse an existing process or use additional processes internally.

4.3 What Does a Process Need to Operate?

A process needs an environment and access to computer resources. The operating system manages and coordinates these resources.

CPU

Executes instructions belonging to the process's runnable threads.

Memory

Holds program instructions, data, and other information needed during execution.

Operating-System Information

Tracks the process's identity, resources, address space, and management information.

Input and Output

Allows the application to interact with files, devices, and other system services.

Important: Process and Thread Are Different

A process provides the environment and resources in which its threads operate.

A process can contain one or more threads. Threads are the execution paths whose instructions are carried out by the CPU.

This means that the CPU scheduler normally selects runnable threads, rather than treating an entire process as one indivisible unit of execution.

4.4 Understanding the Five Basic Process States

A process does not use the CPU continuously from the moment it starts until it finishes. During its lifetime, it can move through different states.

A common introductory operating-systems model describes five basic process states.

  • New: The operating system is creating and preparing the process.
  • Ready: The process has work that can proceed. Its runnable thread is waiting for CPU time.
  • Running: A thread belonging to the process is currently executing instructions on a CPU.
  • Waiting / Blocked: A thread belonging to the process is waiting for an event or operation to finish, such as an input/output operation.
  • Terminated: The process has finished execution or has been terminated.

Visualising the Five Basic States

Important: This Is an Introductory Model

The five-state model is a simplified way to understand process management.

In modern operating systems, individual threads can have different execution states. A process may contain several threads, and those threads do not all have to be in the same state.

The detailed state models and scheduling mechanisms will be studied later.

4.5 Ready Versus Waiting: What Is the Difference?

Both Ready and Waiting / Blocked mean that a thread is not currently executing on the CPU. However, the reason for not executing is different.

Ready

The thread is able to execute, but it is waiting for the scheduler to give it CPU time.

Reason: CPU time is not currently available to that thread.

Waiting / Blocked

The thread cannot continue until a particular event or operation has completed.

Reason: It is waiting for something such as input/output.

Think About Two Different Situations

Situation A: A thread is ready to execute, but another thread is currently using the CPU.

This thread is Ready.

Situation B: A thread requests information from a file and must wait until the operation completes.

This thread is Waiting / Blocked.

Remember: Ready means waiting for CPU time. Waiting / Blocked means waiting for an event.

4.6 How Can a Computer Run Multiple Processes?

Imagine opening a web browser, playing music, and downloading a file at the same time.

These activities may involve several processes and threads. The operating system coordinates their execution and resource use.

One CPU Core

On a simplified single-core system, one thread executes on that core at a time. The operating system can rapidly switch between runnable threads, allowing different activities to make progress.

Multiple CPU Cores

A multicore processor has more than one CPU core. Different cores can execute different threads at the same time.

Two Important Ideas

Concurrency: Multiple activities make progress over time, often by taking turns using the CPU.

Parallelism: Multiple threads actually execute at the same time on different processing cores.

4.7 What Happens When the CPU Switches Between Threads?

A CPU does not have to execute one thread until its entire process finishes before allowing another thread to run.

The operating system can arrange for one running thread to stop using a CPU core and another runnable thread to take its place.

This change of execution is called a context switch.

How Does a Context Switch Work?

  1. One thread is running.

    The CPU is executing instructions belonging to Thread A.

  2. Its execution context is saved.

    The necessary processor state is saved so that Thread A can continue correctly when it runs again.

  3. Another thread is selected.

    The scheduler selects another runnable thread, such as Thread B.

  4. The saved context is restored.

    The processor is prepared to continue executing Thread B from its saved execution context.

Important: A Context Switch Is Not Always a Process Switch

A context switch can happen between threads belonging to different processes.

It can also happen between two threads belonging to the same process.

The saved execution context belongs to the thread being switched out. It can include information such as the program counter and processor register values.

4.8 What Happens When a Process Finishes?

A process may finish because it has completed its work. It may also be stopped or terminated by the operating system or another authorised part of the system.

After termination, the operating system performs the necessary cleanup.

  • Records that the process has terminated.
  • Releases memory and other resources that are no longer needed.
  • Closes or cleans up associated resources as appropriate.
  • Updates process-management information.

Beginner Summary

A process is an executing instance of a program managed by the operating system.

The operating system coordinates its resources, manages its execution, and handles its termination.

During its lifetime, its threads may be ready, running, or waiting. The scheduler coordinates CPU access, and context switching allows different threads to take turns executing.

5. Technical Explanation

5.1 What Happens Inside a Process?

So far, we have understood that a process is an executing instance of a program. Now let's examine how the operating system represents, tracks, and manages that process internally.

A process is more than the program instructions currently being executed. It also has an execution state, memory space, resources, and management information.

The operating system maintains information about each process so that it can schedule execution, manage resources, and resume execution when necessary.

A process can contain one or more threads. Each thread represents an individual path of execution within that process.

5.2 Process Control Block (PCB)

A Process Control Block (PCB) is an operating-system data structure that stores important management information about a process.

Think of the PCB as the operating system's management record for a particular process. It helps the operating system identify the process, track its resources, and manage its overall execution.

A process may contain one or more threads. The operating system therefore needs to maintain information about both the process and its individual threads.

The PCB contains process-level management information. Thread-specific information, such as the saved program counter and CPU register values, is commonly maintained in separate thread-management structures or related kernel data structures.

The exact organisation depends on the operating system. Some systems combine certain information into larger management structures, while others organise it separately.

Important Technical Distinction

The PCB is not the program itself, its memory contents, or the CPU.

It is operating-system information maintained to manage a process. It may also contain references to other structures that help the operating system manage the process's threads and resources.

5.3 What Information Does a PCB Contain?

A PCB and its associated operating-system management structures can contain several categories of information. The following are common teaching categories used to understand their responsibilities.

  • Process identification: Information such as the Process ID (PID) used to identify the process.
  • Process state: Information about the process's lifecycle, such as whether it is being created, executing, waiting, or terminated. In multithreaded systems, individual threads also have their own scheduling states.
  • Thread management: Information or references associated with the threads belonging to the process.
  • CPU scheduling information: Information such as scheduling priority and relationships with scheduling queues. Scheduling information may be maintained separately for individual threads.
  • Memory management information: Information used to manage the process's address space, such as page-table references or related memory-management data.
  • Input/output and file information: Information about resources associated with the process, such as open files and allocated I/O resources.
  • Accounting information: Information such as CPU time consumed and other resource-usage records.

Where Are the Program Counter and CPU Registers Stored?

The program counter and CPU register values are part of a thread's execution context.

When a thread is switched out, the operating system preserves the necessary processor state in thread-specific management information or related kernel structures.

Some introductory operating-system models include these values in the PCB because they describe a process's execution. However, in modern multithreaded systems, treating them as thread-specific is more accurate.

The exact organisation differs between operating systems.

5.4 Process ID (PID)

A Process ID (PID) is a numerical identifier assigned to a process by the operating system.

The operating system uses the PID to distinguish one process from another while managing running processes.

For example, a system may have processes running for a web browser, a music player, and a file manager. Each process can have its own PID.

Process A

PID: 1204

Example: Web browser process.

Process B

PID: 2380

Example: Music player process.

Process C

PID: 3516

Example: File manager process.

Remember

A PID identifies a process. It is not the process's memory address, program instructions, or execution state.

PIDs may be reused by the operating system after a process terminates.

5.5 Program Counter (PC)

The Program Counter (PC) is a processor register that holds the address of the next instruction to execute for the currently running thread.

It helps the processor know where to continue executing instructions.

Imagine a program containing thousands of instructions. A thread executes instructions as part of that program's execution. Its program counter identifies the next instruction address in its execution flow.

A process can contain multiple threads. Each thread has its own program-counter value representing its individual execution progress.

When a thread is interrupted or switched out, the operating system preserves its program-counter value as part of that thread's execution context. When the thread runs again, the appropriate value is restored so execution can continue.

Bookmark Analogy

The program counter is similar to a bookmark that identifies where you should continue reading a book.

Imagine three people reading different chapters of the same book. Each person needs their own bookmark to remember where they stopped.

Similarly, threads belonging to one process can execute different instructions and therefore need separate program-counter values.

The bookmark is only an analogy. Technically, the program counter stores an instruction address, not a physical bookmark or a page number.

5.6 CPU Registers

CPU registers are small, high-speed storage locations inside the processor. They hold values that the processor needs while executing instructions.

A thread's execution may depend on several register values, including data values, addresses, and processor status information.

Although the processor has a physical set of registers, each thread needs its own saved register state so that it can resume execution correctly.

When a thread is running, its current values occupy the processor registers. During a context switch, the operating system preserves the relevant register values for the outgoing thread and restores the saved values required by the incoming thread.

  • General-purpose registers: Hold temporary data, addresses, and intermediate results.
  • Program counter: Identifies the next instruction address.
  • Stack pointer: Identifies the current position of the thread's active stack.
  • Processor status information: Records condition and control information used by the processor.

Important Distinction

Threads do not each have a separate physical CPU register set.

Instead, the processor uses its physical registers for whichever thread is currently executing. The operating system saves and restores the relevant values when switching between threads.

This is how multiple threads can preserve their individual execution progress while sharing the processor.

5.7 What Is a Process Execution Context?

An execution context is the information needed to describe the current execution state of a thread and allow its execution to continue correctly.

For a thread, this includes relevant processor state, such as:

  • Program counter.
  • CPU register values.
  • Stack pointer.
  • Processor status information.

The operating system also maintains other information needed to manage the thread and its relationship with the process.

A process can contain multiple threads. Each thread has its own execution context, while the threads generally share the process's address space and other process-level resources.

What Happens During a Context Switch?

When the operating system switches the CPU from one thread to another, it must preserve the outgoing thread's necessary execution state and restore the incoming thread's saved state.

This allows the incoming thread to continue from its own previous execution point.

A context switch can happen in two important situations:

  • Between threads of the same process: The CPU switches execution from one thread to another, while both threads continue using the same process address space.
  • Between threads of different processes: The CPU switches execution to a thread belonging to another process. This may also involve changing the active address space and associated memory-management context.

Why Is Execution Context Important?

  • It allows a thread to resume correctly.
  • It preserves individual execution progress.
  • It supports switching between threads.
  • It allows multiple threads to share CPU time.
  • It helps the operating system coordinate processor use.

Technical Distinction

A process and a thread are not the same thing.

The process provides the resource-owning environment. The thread provides an individual path of execution within that environment.

The execution context primarily describes the thread's current processor state, rather than a single shared set of CPU register values for the entire process.

5.8 Process Address Space

A process also has an associated address space. This is the range of memory addresses that the process can use, subject to the operating system's memory protection and management rules.

In modern operating systems, a process commonly uses a virtual address space. Virtual addresses are translated by the system's memory-management hardware and operating-system mechanisms into locations in physical memory.

This arrangement helps provide memory protection and gives each process its own organised view of memory.

Threads belonging to the same process generally share that process's address space. This allows them to access shared program code and process data.

Important Distinction

Threads in the same process generally share the process's address space, but each thread has its own execution context and its own stack.

Shared memory does not mean that every part of a thread's execution state is shared with other threads.

5.9 Common Regions of a Process Address Space

A typical process address space can contain several logical regions. Their exact arrangement depends on the operating system, architecture, and program.

  • Text / Code segment: Contains the program's executable instructions.
  • Data segment: Contains global and static variables that have been initialised.
  • BSS segment: Contains global and static variables that are uninitialised or initially zero-initialised.
  • Heap: Provides memory used for dynamic allocation while the program runs.
  • Stack: Supports function calls, local variables, return information, and other call-related data.

Important Memory Concept

The heap and stack are different memory regions with different purposes.

The heap is commonly used for dynamically allocated memory. The stack supports function-call execution and related local data.

Each thread generally has its own stack, while threads belonging to the same process share the process's heap and other shared address-space regions.

These are logical regions of a process's address space. They should not be confused with separate physical memory chips.

5.11 How Do the PCB and Process Memory Work Together?

The PCB and the process address space serve different but related purposes.

  • The PCB contains operating-system management information about the process.
  • The process address space provides the process with its organised view of memory.
  • Memory-management information helps the operating system and hardware manage and protect that address space.
  • Thread-management information preserves the execution state needed to resume individual threads.
  • Threads belonging to the same process generally share the process's address space and process-level resources.

Together, these mechanisms allow the operating system to manage a process and its threads as they execute, wait, resume, and eventually terminate.

Technical Summary

A process is an executing instance of a program with an associated address space, execution state, and operating-system-managed resources.

The PCB stores process-level management information. The PID identifies the process. Each thread has its own execution context, including its program counter and saved CPU registers. The process address space organises the memory available to the process and is generally shared by its threads.

6.1 Why Does the Operating System Need Process Information?

The operating system must distinguish these processes and keep track of their execution, CPU requirements, memory information, and associated resources.

Without this management information, the operating system would have difficulty coordinating the execution of different programs.

Process-management information helps the operating system:

  • Identify individual processes.
  • Track their current states.
  • Preserve execution information.
  • Manage CPU scheduling.
  • Keep track of memory-management information.
  • Coordinate input/output and other resources.

6.3 How Are Processes and Threads Related?

A process provides the environment and resources in which its threads operate. A thread is an individual path of execution within a process.

A process can contain one thread or multiple threads. When multiple threads belong to the same process, they generally share the process's address space and many process-level resources.

However, each thread has its own execution context. This includes its own program counter, saved CPU register values, and stack.

6.6 Is the PCB the Same as the Process's Memory?

No. The PCB, the process address space, and the CPU are three different things.

  • PCB: A conceptual representation of operating-system management information about a process.
  • Process address space: The organised virtual memory space associated with a process.
  • CPU registers: Hardware storage locations inside the processor.
  • Saved thread context: Information preserved so an individual thread can resume execution later.

Important Technical Distinction

The PCB is not the process's entire memory, and it is not the CPU itself.

Some process-management information may refer to other structures or resources. This does not mean that all those structures are physically stored inside one PCB.

Similarly, scheduling and execution-context information is often maintained at the individual thread level.

11. Common Mistakes and Misconceptions

When learning about processes, it is easy to confuse related concepts or make incorrect assumptions about how an operating system works.

Let's examine ten common misconceptions and understand what actually happens inside an operating system.

11.1 Ten Common Process Misconceptions

Each example separates a common misunderstanding from the technically correct explanation.

11.1.1 Program and Process Are the Same

MYTH — Common misconception: A program and a process are exactly the same thing.

REALITY — Correct understanding: A program is a set of instructions stored as a file. A process is an instance of a program being executed, together with its execution state and associated resources.

EXAMPLE: A text editor stored on your device is a program. When you launch it, the operating system creates a process to manage its execution.

Remember: Program = instructions. Process = executing instance.

11.1.2 Every Process Is Always Running

MYTH — Common misconception: Every process is constantly using the CPU.

REALITY — Correct understanding: In the classic five-state model, a process can be New, Ready, Running, Waiting, or Terminated. Running means its execution is currently taking place on a CPU.

EXAMPLE: A music application waiting for data from storage may be blocked rather than executing application instructions on the CPU.

Remember: Existing on a computer does not mean continuously using the CPU.

11.1.3 Ready and Waiting Mean the Same Thing

MYTH — Common misconception: Ready and Waiting both mean that a process is waiting, so they are identical.

REALITY — Correct understanding: Ready means the execution is prepared to run but needs CPU time. Waiting means it cannot continue until a particular event or operation is completed.

EXAMPLE: A Ready process needs the scheduler to select it. A process waiting for a file-reading operation needs that operation to complete.

Remember: Ready = waiting for CPU. Waiting = waiting for an event.

11.1.4 A Ready Process Immediately Gets the CPU

MYTH — Common misconception: As soon as a process enters Ready, it starts executing.

REALITY — Correct understanding: A Ready process must wait until the CPU scheduler selects its execution work. The dispatcher then transfers CPU control to the selected work.

EXAMPLE: Several processes may have Ready threads at the same time. On a single CPU core, only one thread can execute on that core at a time.

Remember: Ready means eligible to run, not currently running.

11.1.5 Scheduler and Dispatcher Are the Same

MYTH — Common misconception: The CPU scheduler and dispatcher perform exactly the same job.

REALITY — Correct understanding: The scheduler selects which eligible execution should run next. The dispatcher carries out the handover, including the necessary context-switching work and transfer of CPU control.

EXAMPLE: Think of the scheduler as choosing the next passenger and the dispatcher as helping that passenger take their seat.

Remember: Scheduler = selects. Dispatcher = hands over.

11.1.6 Context Switching Is Simply Executing Another Process

MYTH — Common misconception: A context switch is simply the execution of another process.

REALITY — Correct understanding: A context switch involves saving the necessary CPU execution context of one thread and restoring the context of another. This allows execution to resume from the appropriate point.

EXAMPLE: The operating system saves information such as the program counter and relevant CPU registers before switching execution to another thread.

Remember: Context switching changes which execution context is using the CPU; it does not copy the entire process memory.

11.1.7 A Waiting Process Continues Using the CPU

MYTH — Common misconception: A process waiting for I/O continues consuming CPU time while it waits.

REALITY — Correct understanding: In a blocking I/O operation, the blocked thread does not execute its application instructions while waiting for the required event. The CPU can execute another Ready thread.

EXAMPLE: While a text editor waits for a storage operation, another Ready thread can use the CPU.

Remember: Waiting for I/O does not mean continuously executing on the CPU.

11.1.8 Every Application Has Only One Process

MYTH — Common misconception: One application always corresponds to exactly one process.

REALITY — Correct understanding: An application may use multiple processes, and a single process may contain multiple threads. The relationship depends on the application's design and the operating system.

EXAMPLE: A modern web browser may use separate processes for page rendering, browser services, or other tasks. Its exact architecture varies.

Remember: One application does not necessarily mean one process.

11.1.9 A Terminated Process Is Temporarily Inactive

MYTH — Common misconception: A terminated process is simply a process that is temporarily inactive.

REALITY — Correct understanding: A terminated process has finished execution or has been stopped. The same process instance does not return to Ready or Running. The operating system handles its remaining cleanup.

EXAMPLE: When a text editor process exits, it no longer continues executing as that process. Some operating systems may temporarily retain exit information until another process collects it.

Remember: Terminated means execution has ended, not paused.

11.1.10 Every Process Follows One Fixed Lifecycle

MYTH — Common misconception: Every process must follow exactly the same sequence of state transitions.

REALITY — Correct understanding: A process can move repeatedly between Ready, Running, and Waiting. Its actual journey depends on scheduling decisions, I/O requests, events, and how execution ends.

EXAMPLE: A process may run, wait for I/O, return to Ready, run again, and repeat this cycle many times before termination.

Remember: A process lifecycle can contain repeated state transitions.

12. Advantages and Limitations of Processes

Understanding the Trade-Off

Processes provide the operating system with a structured way to manage executing programs. They support multitasking, memory protection, resource management, and responsive computing.

However, creating and managing processes also requires memory, CPU time, and coordination. These costs introduce performance challenges and additional complexity.

Understanding both sides helps explain why processes are essential to modern operating systems and why they must be managed carefully.

12.1 Advantages of Processes

Processes provide several important benefits that help an operating system manage applications and their execution.

1. Multitasking

How it helps:

  • Allows multiple applications to make progress during overlapping periods.
  • The operating system schedules execution among competing processes and threads.
  • Multiple threads can execute simultaneously on different CPU cores.

Example: Listening to music while browsing the internet and downloading a file.

Remember: Scheduling enables multitasking; multiple CPU cores can provide true parallel execution.

2. Process Isolation

How it helps:

  • Processes generally have separate virtual address spaces.
  • Memory protection helps prevent unauthorized access between processes.
  • A failure in one process is less likely to directly damage another process.

Example: A crash in a text editor does not necessarily crash a separate music player.

Remember: Isolation reduces interference; it does not guarantee complete protection from every failure.

3. Better Resource Management

How it helps:

  • The operating system manages CPU allocation.
  • It coordinates memory, storage, and I/O resource usage.
  • It manages competing requests from different processes.

Example: The CPU scheduler selects eligible execution from the Ready queue.

Remember: The operating system coordinates access to limited computer resources.

4. Improved Responsiveness

How it helps:

  • A thread waiting for blocking I/O can become blocked.
  • The CPU can execute another Ready thread while the operation is pending.
  • This helps the system make progress instead of leaving the CPU idle unnecessarily.

Example: A browser waiting for a storage operation while another application continues executing.

Remember: Waiting for I/O does not necessarily prevent other work from progressing.

5. Controlled Execution

How it helps:

  • Every process has identifiable management information.
  • The operating system tracks process and thread execution.
  • It supports operations such as creation, scheduling, suspension, resumption, and termination.

Example: The operating system can terminate an unresponsive application.

Remember: Process management gives the operating system control over application execution.

12.2 Limitations and Challenges of Processes

Although processes provide important benefits, creating and managing them introduces costs and technical challenges.

1. Process Creation Overhead

Why it is a limitation:

  • Creating a process requires operating-system operations.
  • The OS establishes process-management structures and execution resources.
  • Creation consumes time and memory.

Example: Starting a new application requires additional work compared with continuing an already-running process.

Remember: Creating and managing a process has a cost.

2. Context-Switching Overhead

Why it is a limitation:

  • The OS saves the outgoing execution context.
  • It restores the incoming execution context.
  • The switching work consumes CPU time without directly advancing the applications' own instructions.

Example: Frequent switching between execution contexts can add overhead to system activity.

Remember: Context switching can happen between different processes or between threads belonging to the same process.

3. Memory Consumption

Why it is a limitation:

  • Processes require memory for management structures and execution.
  • Multiple processes can increase total memory demand.
  • Some memory, such as shared libraries, can be shared between processes.

Example: Opening many memory-intensive applications can put pressure on available RAM.

Remember: Memory requirements vary; process memory is not necessarily duplicated in full.

4. Inter-Process Communication Complexity

Why it is a limitation:

  • Separate processes sometimes need to exchange information.
  • Communication may use pipes, sockets, message queues, or shared memory.
  • Designing and managing communication adds complexity.

Example: Two separate applications exchanging information through a communication channel.

Remember: Separate address spaces provide protection, but communication requires an appropriate mechanism.

5. Synchronization Problems

Why it is a limitation:

  • Processes or threads may access shared resources.
  • Poor coordination can produce race conditions.
  • Incorrect resource coordination can also lead to deadlocks.

Example: Two processes attempt to update the same shared data without appropriate coordination.

Remember: Shared resources require correct synchronization.

6. Resource Contention

Why it is a limitation:

  • Processes and threads compete for limited resources.
  • CPU time, memory, storage, and I/O devices can become bottlenecks.
  • Heavy competition can reduce overall system performance.

Example: Several demanding applications compete for CPU time and available memory.

Remember: When demand exceeds available resources, performance can suffer.

12.4 Understanding the Trade-Off

Processes provide the operating system with a structured way to manage executing programs. They support multitasking, protection, resource management, and responsiveness.

However, these benefits come with costs: process creation, memory consumption, context switching, communication, synchronization, and competition for resources.

The operating system must balance these competing demands to maintain good performance and reliable execution.

The central lesson: Processes make modern multitasking systems possible, but effective process management requires balancing their benefits against their overhead.

13. Connections to Other Operating-System Concepts

Understanding the Connections

A process does not operate in isolation. It depends on several operating-system mechanisms that cooperate to execute programs, manage resources, and respond to events.

Think of process management as one part of a much larger system. The operating system coordinates the CPU, memory, threads, files, devices, and communication between processes.

In this section, we will connect the process concept to the other major ideas that make an operating system work.

13.1 Process and Program

The Relationship

  • A program is a passive set of instructions stored on a device.
  • A process is an instance of a program in execution.
  • One program can have multiple process instances.
  • Each process has its own process identity and execution state.
  • The operating system manages the resources associated with each process.

Analogy: A recipe is like a program. Someone actively following the recipe is like a process. The written instructions do not perform the cooking; the person carrying them out does.

Example: Opening two independent instances of an application can create two separate processes. The exact behaviour depends on how the application is designed.

Remember: A program describes what instructions can be executed. A process represents an executing instance managed by the operating system.

13.2 Process and Thread

The Relationship

  • A process provides resources and an environment for execution.
  • A thread is an individual path of execution within a process.
  • A process can contain one or multiple threads.
  • Threads in the same process normally share its address space and many process resources.
  • Each thread maintains its own execution context, including its registers, program counter, and stack.

Analogy: A process is a workshop. Threads are workers operating inside that workshop. They share facilities but perform their own tasks.

Example: A browser may use multiple threads for interface operations, networking, rendering, and other activities.

Important distinction: Threads share many resources, but each thread has its own execution context. A problem in one thread can still affect other threads in the same process because they share resources.

13.3 Process and Process Control Block (PCB)

The Relationship

  • The operating system maintains information about each process.
  • This information is organised in a Process Control Block (PCB), or an equivalent process-management structure.
  • It includes information such as process ID, process state, scheduling information, and memory-management references.
  • The operating system uses this information to manage and track the process.
  • Thread-specific execution information is generally maintained in separate thread-management structures.

Analogy: A PCB is like an employee's official administrative record. It contains important information needed to manage that employee's work.

Example: When the operating system performs a context switch, it saves and restores the relevant execution information for the thread being switched.

Remember: The PCB helps the operating system keep track of a process. It is not the process itself, nor does it contain every byte of the process's memory.

13.4 Process and CPU Scheduling

The Relationship

  • Multiple runnable threads may compete for CPU time.
  • The scheduler selects an eligible thread for execution.
  • The dispatcher carries out the handover of CPU control.
  • Scheduling policies help determine how CPU time is distributed.
  • When a thread waits for an event, another eligible thread may be selected.

Analogy: Imagine several workers waiting to use one shared machine. A manager decides who should use it next, and the machine operator carries out the handover.

Example: While one thread waits for a file-reading operation to complete, the scheduler may select another ready thread.

Technical note: Introductory process diagrams often describe scheduling in terms of processes. In many modern operating systems, the actual scheduling unit is a thread.

13.5 Process and Memory Management

The Relationship

  • Each process generally has its own virtual address space.
  • A program uses virtual addresses when accessing memory.
  • Page tables help define how virtual addresses map to physical memory.
  • The Memory Management Unit (MMU) performs hardware-assisted address translation.
  • Memory protection helps prevent one process from accessing memory it is not permitted to access.
  • Physical memory is managed and allocated as processes execute.

Analogy: Imagine that each process has its own numbered map of a building. The numbers on one map do not have to refer to the same physical rooms as the numbers on another map. The memory management system helps translate those virtual numbers into actual memory locations.

Example: Two processes can use the same virtual address without necessarily accessing the same physical memory location.

Connection: Virtual memory gives processes a structured view of memory, while address translation and protection mechanisms help the operating system manage access safely.

13.6 Process and Interrupts

The Relationship

  • An interrupt notifies the CPU that an event requires attention.
  • Hardware devices can generate interrupts to signal events such as I/O completion.
  • The processor transfers control to an appropriate interrupt-handling mechanism.
  • The operating system handles the event and updates relevant information.
  • The OS may change a process or thread's state if the event satisfies a condition it was waiting for.

Analogy: An interrupt is like a doorbell. It notifies someone that an event requires attention. The doorbell itself does not decide what happens next.

Example: A device signals that an I/O operation has completed. The operating system handles the event and may move the waiting thread to the Ready state.

Important distinction: An interrupt does not automatically make a process Ready. The operating system must determine what the event means and whether the waiting condition has been met.

13.7 Process and Inter-Process Communication (IPC)

The Relationship

  • Separate processes sometimes need to exchange information.
  • Inter-Process Communication (IPC) provides mechanisms for this exchange.
  • Common mechanisms include pipes, sockets, message queues, and shared memory.
  • Some IPC mechanisms transfer messages; others allow processes to access shared memory.
  • Synchronization may be needed when processes access shared information.

Analogy: Imagine two separate offices communicating through a telephone, a message service, or a shared noticeboard.

Example: A client application communicates with a separate server process through a network socket.

Important distinction: Communication is about exchanging information. Synchronization is about coordinating access and timing so that shared resources are used correctly.

13.8 Process and File System

The Relationship

  • Processes often need to create, open, read, write, and close files.
  • The operating system provides interfaces for file operations.
  • Programs normally request file services through system calls or operating-system APIs.
  • The operating system and file-system components handle the requested operations.
  • Applicable permissions and access controls determine whether an operation is allowed.

Analogy: A process is like an employee requesting documents from a records department. The department checks the request and provides access when authorised.

Example: A text editor requests that the operating system open and read a document. Later, it may request that changes be written back to the file.

13.9 Process and System Calls

The Relationship

  • A program sometimes needs services that only the operating system can provide.
  • A system call provides a controlled interface for requesting kernel services.
  • Requests may involve file operations, process creation, memory management, and device I/O.
  • The system call mechanism transfers control to the operating system's service-handling code.
  • The kernel handles the request according to operating-system rules and permissions.

Analogy: A system call is like submitting an official service request to an organisation's central administration. The administration handles the request according to its rules.

Example: A program requests the operating system to create another process or open a file.

Remember: A system call is not simply an ordinary function call. It provides a controlled way for a program to request operating-system services.

15.3 Process Lifecycle Revision

A process moves through different states during its lifetime. The operating system tracks these states to manage execution.

  • New: The process is being created.
  • Ready: The process is prepared to execute and is waiting for CPU allocation.

Important State Transitions

  • New → Ready: The process is admitted into the ready state.

  • Running → Waiting: The process must wait for an event or operation, such as an I/O request, to complete.
  • Waiting → Ready: The required event occurs and the process becomes eligible for CPU scheduling again.
  • Running → Terminated: The process finishes or is terminated.

Key distinction: A process in the Ready state is waiting for CPU time. A process in the Waiting state is waiting for an event.

  4. Context Switching: The operating system saves the execution context of one process or thread and restores another.
  5. Memory Management: The operating system manages process address spaces, memory allocation and protection, with hardware support such as the Memory Management Unit (MMU).
  6. Communication: Processes exchange information using IPC mechanisms such as pipes, message queues, sockets and shared memory.
  7. Process Termination: The operating system performs the necessary cleanup and releases resources associated with the process.

15.9 The Big Picture: Why Processes Matter

A computer runs many programs and performs many activities. The operating system needs a way to organise, track, schedule and control their execution.

Processes provide an important abstraction for this work. They allow the operating system to manage executing programs, coordinate their access to resources, protect their memory and support communication between them.

Final takeaway: Process management is one of the central responsibilities of an operating system. It helps turn a collection of competing programs into an organised and manageable computing environment.
