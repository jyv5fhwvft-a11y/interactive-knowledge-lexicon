OPERATING SYSTEMS | CONCEPT 002

Process

A Program in Execution

What happens when a computer actually runs a program?

A process is a program that is currently executing on a computer.

When you open an application, the operating system creates and manages a process so that the program can use the computer's resources, such as the CPU and memory.

1. Concept Identity and Definition

Concept ID: IKL-OS-002

Concept: Process

Subject: Operating Systems

Topic: Process Management

What Is a Process?

A process is an instance of a program that has been started and is being managed by an operating system. It has its own execution context, address space, one or more threads, and associated resources and management information.

In Simple Words

A program contains instructions. A process is an instance of that program being managed while it executes or waits to continue execution.

Program vs Process: What Is the Difference?

Program

A program is a passive set of instructions stored in a file.

  • Exists as stored code
  • Does not execute by itself
  • Waits to be started

Process

A process is an active instance of a program managed by the operating system.

  • Has an execution context
  • Uses memory and other resources
  • Can execute or wait

How Does a Program Become a Process?

What Does a Process Include?

A process is more than just the program's instructions. The operating system must keep track of several elements so that execution can be managed correctly.

  • Address space: The memory space associated with the process.
  • Threads: One or more execution paths within the process.
  • Execution context: Information needed to pause and resume execution, such as processor register values.
  • Resources: Resources associated with the process, such as open files and other operating-system objects.
  • Management information: Information the operating system maintains about the process, including its identity and state.

Important: Process vs Thread

A process provides the environment and resources in which its threads operate. The CPU schedules and executes threads, rather than treating the process as one indivisible execution unit.

Can One Program Have Multiple Processes?

Yes. A program can be started more than once, creating multiple process instances. Each instance is managed separately by the operating system.

Why Does the Operating System Manage Processes?

Several programs may need the computer's CPU, memory, storage and input/output devices at the same time. The operating system coordinates their use.

Understanding Process Isolation

Processes are given controlled memory and resource access so that one process cannot freely interfere with another. Isolation is not absolute: processes can communicate and share selected resources through operating-system mechanisms.

What You Should Understand

After studying this section, you should be able to:

  • Define a process in operating-system terminology.
  • Distinguish a program from a process.
  • Identify the main elements associated with a process.
  • Explain the relationship between processes and threads.
  • Describe why the operating system manages processes.
  • Explain how one program can have multiple instances.

2. Process Explained Like You're Five

2.1 What Is a Process?

Imagine you have a colour-by-number book. It contains pictures and instructions telling you which colours to use.

When the book is sitting on your table, the instructions are there, but nobody is colouring the picture.

Now imagine picking up your crayons and following the instructions. You are actively doing something: colouring the picture.

A computer works in a similar way. A program is a set of instructions stored on the computer. When the operating system starts managing an executing instance of that program, it is called a process.

Think of It This Way

Program: The instructions waiting to be followed.

Process: Those instructions being carried out by the computer.

Let's follow what happens when you open an application on your computer.

    The program is stored on the computer. It contains instructions that tell the computer what to do.

  2. Second: You ask the computer to open it.

    You tap or click an application, such as Calculator.

  3. Third: The operating system creates and manages a process.

    The operating system prepares an executing instance of the program and manages the resources it needs to do its work.

Not necessarily. A process does not have to use the CPU continuously from the moment it starts until it finishes.

Sometimes it waits for its turn to use the CPU. At other times, it may wait for something such as user input.

The operating system manages these activities. We will explore the different process states in a later section.

Program: A set of instructions stored on a computer.

Process: An executing instance of a program, managed by the operating system.

In one sentence: A program is the instructions; a process is an instance of those instructions being executed.

3. Analogy and Mental Model

3.1 Imagine a Busy Restaurant Kitchen

Imagine a busy restaurant where several customers place orders for food.

Each order describes what a customer wants. The kitchen has recipes, chefs, cooking stations, ingredients, and equipment needed to prepare those orders.

The kitchen manager organises the work. The manager keeps track of orders, coordinates the available resources, and helps decide which order should be handled next.

A computer system works in a comparable way. When you start an application, the operating system creates and manages a process. It coordinates the resources needed for that process to execute.

The Main Idea

Think of a process as a particular order being carried out in the kitchen. The operating system is like the kitchen manager coordinating the work.

This is a learning analogy. A computer process is not literally a food order, and an operating system is not a person.

3.3 Follow One Order Through the Kitchen

Let's follow one customer's order and see how the same general ideas appear in a computer.

  1. A recipe exists.

    A recipe contains instructions for preparing a dish. Similarly, a program contains instructions stored on a computer.

  2. A customer places an order.

    The restaurant receives a request to prepare a dish. Similarly, a user may request that an application run.

  3. The kitchen begins preparing the order.

    The order becomes work being carried out. Similarly, the operating system creates and manages a process when a program is started.

  4. The kitchen manager coordinates the work.

    The manager keeps track of orders and coordinates available resources. Similarly, the operating system manages processes and their resource access.

  5. The order may need to wait.

    A kitchen may have different reasons for an order to wait. A cooking station may be busy, or an ingredient may not have arrived.

  6. The order is completed.

    The finished dish leaves the kitchen. Similarly, a process terminates when its execution ends.

3.4 The Real Operating-System Concepts

The restaurant analogy helps us understand the general idea. Now let's connect it to the actual computer concepts.

  • Program: A stored set of instructions that describes what a computer should do.
  • Process: An executing instance of a program that the operating system manages.
  • Operating system: System software that manages processes and coordinates access to computer resources.
  • CPU: The processor that executes instructions belonging to running threads.
  • Memory: Holds the instructions, data and other information needed during execution.
  • Process scheduling: The operating system's method of deciding which ready thread should receive CPU time.
  • Ready: A process has work that can proceed. More precisely, its runnable thread is waiting for CPU time.
  • Waiting / Blocked: A thread belonging to a process is waiting for an event or operation, such as input/output, to finish.
  • Termination: The process has finished its execution and is being or has been cleaned up.

Important: Ready and Waiting Are Different

Imagine two restaurant orders.

Order A: All ingredients are available, but the cooking station is busy. The order is ready for preparation.

Order B: The order cannot continue because a required ingredient has not arrived.

In a computer:

  • Ready: Waiting for CPU time.
  • Waiting / Blocked: Waiting for an event or operation.

These are two different reasons why a process may not currently be executing.

Important: The Process Is Not the CPU

In the restaurant analogy, the order represents the process. The chef and cooking station represent the ability to carry out the work.

In a computer, a process is the managed environment containing one or more threads. The CPU executes instructions belonging to those threads.

A process does not need to use the CPU continuously. It may receive CPU time, pause while another thread runs, or wait for an event such as a file operation.

The detailed process states and scheduling mechanisms will be explained in later sections.

Important: An Analogy Is Not the Actual Mechanism

A restaurant kitchen helps us imagine how work is organised, but a computer does not operate exactly like a restaurant.

A chef is a person who performs physical work. A CPU is an electronic processor that executes machine instructions.

The operating system uses scheduling algorithms, data structures, memory management and hardware mechanisms. It does not manage processes by behaving like a human manager.

Use the analogy to understand the relationships, not to assume that every restaurant activity has an exact technical equivalent.

3.5 A Second Mental Model: Your Desk and a Bookmark

Imagine reading a book at your desk. You stop reading to answer the telephone.

Before leaving, you place a bookmark on the page where you stopped.

When you return, the bookmark helps you find your place and continue reading.

A computer also needs to preserve important execution information when a thread stops using the CPU temporarily.

During a context switch, the operating system saves the necessary execution context of the thread being switched out and restores the saved context of the thread being switched in.

What Does the Bookmark Represent?

The bookmark represents the idea of remembering where execution should continue.

In a computer, the saved execution context contains more than a simple position. It can include information such as the program counter and processor register values.

The bookmark is only an analogy. It does not represent the complete technical state of a process or thread.

Does Every Context Switch Mean Switching Processes?

No. A context switch can occur between threads belonging to different processes. It can also occur between threads belonging to the same process.

This is why it is important to understand that a process can contain one or more threads.

Remember the Two Mental Models

Restaurant kitchen: Helps explain processes, execution, resource coordination, scheduling, waiting and completion.

Book and bookmark: Helps explain why execution information must be saved and restored when a thread stops and later resumes.

4. Beginner Explanation

4.1 What Actually Happens When You Open an Application?

Imagine tapping the Calculator application on your computer or tablet. You expect the Calculator window to appear and allow you to perform calculations.

Behind that simple action, the operating system performs several jobs. It starts the application, establishes an environment in which it can operate, manages its resources, and coordinates its execution.

The operating system represents a running instance of the application as a process.

The Important Idea

Opening an application is not simply displaying a window. It involves creating or activating the work environment that allows the application to operate.

4.2 How Does the Operating System Create a Process?

Let's follow a simplified example of what can happen when you request an application to open.

  1. You request an application.

    You tap or click an application icon, such as Calculator.

  2. The operating system receives the request.

    The operating system handles the request and begins the appropriate application-starting procedure.

  3. The operating system prepares the process.

    It establishes an execution environment, creates the necessary management information, and arranges the memory and resources needed by the application.

  4. The process becomes ready to execute.

    Its runnable thread can enter the Ready state and wait for an opportunity to receive CPU time.

  5. A thread receives CPU time.

    The scheduler selects a runnable thread. The CPU can then execute the instructions belonging to that thread.

A Small Technical Detail

This is a simplified learning sequence. Actual application-starting procedures differ between operating systems. Some applications may reuse an existing process or use additional processes internally.

4.3 What Does a Process Need to Operate?

A process needs an environment and access to computer resources. The operating system manages and coordinates these resources.

CPU

Executes instructions belonging to the process's runnable threads.

Memory

Holds program instructions, data, and other information needed during execution.

Operating-System Information

Tracks the process's identity, resources, address space, and management information.

Input and Output

Allows the application to interact with files, devices, and other system services.

Important: Process and Thread Are Different

A process provides the environment and resources in which its threads operate.

A process can contain one or more threads. Threads are the execution paths whose instructions are carried out by the CPU.

This means that the CPU scheduler normally selects runnable threads, rather than treating an entire process as one indivisible unit of execution.

4.4 Understanding the Five Basic Process States

A process does not use the CPU continuously from the moment it starts until it finishes. During its lifetime, it can move through different states.

A common introductory operating-systems model describes five basic process states.

  • New: The operating system is creating and preparing the process.
  • Ready: The process has work that can proceed. Its runnable thread is waiting for CPU time.
  • Running: A thread belonging to the process is currently executing instructions on a CPU.
  • Waiting / Blocked: A thread belonging to the process is waiting for an event or operation to finish, such as an input/output operation.
  • Terminated: The process has finished execution or has been terminated.

Visualising the Five Basic States

Important: This Is an Introductory Model

The five-state model is a simplified way to understand process management.

In modern operating systems, individual threads can have different execution states. A process may contain several threads, and those threads do not all have to be in the same state.

The detailed state models and scheduling mechanisms will be studied later.

4.5 Ready Versus Waiting: What Is the Difference?

Both Ready and Waiting / Blocked mean that a thread is not currently executing on the CPU. However, the reason for not executing is different.

Ready

The thread is able to execute, but it is waiting for the scheduler to give it CPU time.

Reason: CPU time is not currently available to that thread.

Waiting / Blocked

The thread cannot continue until a particular event or operation has completed.

Reason: It is waiting for something such as input/output.

Think About Two Different Situations

Situation A: A thread is ready to execute, but another thread is currently using the CPU.

This thread is Ready.

Situation B: A thread requests information from a file and must wait until the operation completes.

This thread is Waiting / Blocked.

Remember: Ready means waiting for CPU time. Waiting / Blocked means waiting for an event.

4.6 How Can a Computer Run Multiple Processes?

Imagine opening a web browser, playing music, and downloading a file at the same time.

These activities may involve several processes and threads. The operating system coordinates their execution and resource use.

One CPU Core

On a simplified single-core system, one thread executes on that core at a time. The operating system can rapidly switch between runnable threads, allowing different activities to make progress.

Multiple CPU Cores

A multicore processor has more than one CPU core. Different cores can execute different threads at the same time.

Two Important Ideas

Concurrency: Multiple activities make progress over time, often by taking turns using the CPU.

Parallelism: Multiple threads actually execute at the same time on different processing cores.

4.7 What Happens When the CPU Switches Between Threads?

A CPU does not have to execute one thread until its entire process finishes before allowing another thread to run.

The operating system can arrange for one running thread to stop using a CPU core and another runnable thread to take its place.

This change of execution is called a context switch.

How Does a Context Switch Work?

  1. One thread is running.

    The CPU is executing instructions belonging to Thread A.

  2. Its execution context is saved.

    The necessary processor state is saved so that Thread A can continue correctly when it runs again.

  3. Another thread is selected.

    The scheduler selects another runnable thread, such as Thread B.

  4. The saved context is restored.

    The processor is prepared to continue executing Thread B from its saved execution context.

Important: A Context Switch Is Not Always a Process Switch

A context switch can happen between threads belonging to different processes.

It can also happen between two threads belonging to the same process.

The saved execution context belongs to the thread being switched out. It can include information such as the program counter and processor register values.

4.8 What Happens When a Process Finishes?

A process may finish because it has completed its work. It may also be stopped or terminated by the operating system or another authorised part of the system.

After termination, the operating system performs the necessary cleanup.

  • Records that the process has terminated.
  • Releases memory and other resources that are no longer needed.
  • Closes or cleans up associated resources as appropriate.
  • Updates process-management information.

Beginner Summary

A process is an executing instance of a program managed by the operating system.

The operating system coordinates its resources, manages its execution, and handles its termination.

During its lifetime, its threads may be ready, running, or waiting. The scheduler coordinates CPU access, and context switching allows different threads to take turns executing.

What You Should Understand

After studying this section, you should be able to:

  • Explain what happens when an application is opened.
  • Describe, at a beginner level, how an operating system prepares and manages a process.
  • Identify the main resources a process needs.
  • Explain the five basic process states.
  • Distinguish Ready from Waiting / Blocked.
  • Explain the difference between single-core and multicore execution.
  • Describe the basic purpose of a context switch.
  • Explain what happens when a process terminates.

5. Technical Explanation

5.1 What Happens Inside a Process?

So far, we have understood that a process is an executing instance of a program. Now let's examine how the operating system represents, tracks, and manages that process internally.

A process is more than the program instructions currently being executed. It also has an execution state, memory space, resources, and management information.

The operating system maintains information about each process so that it can schedule execution, manage resources, and resume execution when necessary.

A process can contain one or more threads. Each thread represents an individual path of execution within that process.

5.2 Process Control Block (PCB)

A Process Control Block (PCB) is an operating-system data structure that stores important management information about a process.

Think of the PCB as the operating system's management record for a particular process. It helps the operating system identify the process, track its resources, and manage its overall execution.

A process may contain one or more threads. The operating system therefore needs to maintain information about both the process and its individual threads.

The PCB contains process-level management information. Thread-specific information, such as the saved program counter and CPU register values, is commonly maintained in separate thread-management structures or related kernel data structures.

The exact organisation depends on the operating system. Some systems combine certain information into larger management structures, while others organise it separately.

Important Technical Distinction

The PCB is not the program itself, its memory contents, or the CPU.

It is operating-system information maintained to manage a process. It may also contain references to other structures that help the operating system manage the process's threads and resources.

5.3 What Information Does a PCB Contain?

A PCB and its associated operating-system management structures can contain several categories of information. The following are common teaching categories used to understand their responsibilities.

  • Process identification: Information such as the Process ID (PID) used to identify the process.
  • Process state: Information about the process's lifecycle, such as whether it is being created, executing, waiting, or terminated. In multithreaded systems, individual threads also have their own scheduling states.
  • Thread management: Information or references associated with the threads belonging to the process.
  • CPU scheduling information: Information such as scheduling priority and relationships with scheduling queues. Scheduling information may be maintained separately for individual threads.
  • Memory management information: Information used to manage the process's address space, such as page-table references or related memory-management data.
  • Input/output and file information: Information about resources associated with the process, such as open files and allocated I/O resources.
  • Accounting information: Information such as CPU time consumed and other resource-usage records.

Where Are the Program Counter and CPU Registers Stored?

The program counter and CPU register values are part of a thread's execution context.

When a thread is switched out, the operating system preserves the necessary processor state in thread-specific management information or related kernel structures.

Some introductory operating-system models include these values in the PCB because they describe a process's execution. However, in modern multithreaded systems, treating them as thread-specific is more accurate.

The exact organisation differs between operating systems.

5.4 Process ID (PID)

A Process ID (PID) is a numerical identifier assigned to a process by the operating system.

The operating system uses the PID to distinguish one process from another while managing running processes.

For example, a system may have processes running for a web browser, a music player, and a file manager. Each process can have its own PID.

Process A

PID: 1204

Example: Web browser process.

Process B

PID: 2380

Example: Music player process.

Process C

PID: 3516

Example: File manager process.

Remember

A PID identifies a process. It is not the process's memory address, program instructions, or execution state.

PIDs may be reused by the operating system after a process terminates.

5.5 Program Counter (PC)

The Program Counter (PC) is a processor register that holds the address of the next instruction to execute for the currently running thread.

It helps the processor know where to continue executing instructions.

Imagine a program containing thousands of instructions. A thread executes instructions as part of that program's execution. Its program counter identifies the next instruction address in its execution flow.

A process can contain multiple threads. Each thread has its own program-counter value representing its individual execution progress.

When a thread is interrupted or switched out, the operating system preserves its program-counter value as part of that thread's execution context. When the thread runs again, the appropriate value is restored so execution can continue.

Bookmark Analogy

The program counter is similar to a bookmark that identifies where you should continue reading a book.

Imagine three people reading different chapters of the same book. Each person needs their own bookmark to remember where they stopped.

Similarly, threads belonging to one process can execute different instructions and therefore need separate program-counter values.

The bookmark is only an analogy. Technically, the program counter stores an instruction address, not a physical bookmark or a page number.

5.6 CPU Registers

CPU registers are small, high-speed storage locations inside the processor. They hold values that the processor needs while executing instructions.

A thread's execution may depend on several register values, including data values, addresses, and processor status information.

Although the processor has a physical set of registers, each thread needs its own saved register state so that it can resume execution correctly.

When a thread is running, its current values occupy the processor registers. During a context switch, the operating system preserves the relevant register values for the outgoing thread and restores the saved values required by the incoming thread.

  • General-purpose registers: Hold temporary data, addresses, and intermediate results.
  • Program counter: Identifies the next instruction address.
  • Stack pointer: Identifies the current position of the thread's active stack.
  • Processor status information: Records condition and control information used by the processor.

Important Distinction

Threads do not each have a separate physical CPU register set.

Instead, the processor uses its physical registers for whichever thread is currently executing. The operating system saves and restores the relevant values when switching between threads.

This is how multiple threads can preserve their individual execution progress while sharing the processor.

5.7 What Is a Process Execution Context?

An execution context is the information needed to describe the current execution state of a thread and allow its execution to continue correctly.

For a thread, this includes relevant processor state, such as:

  • Program counter.
  • CPU register values.
  • Stack pointer.
  • Processor status information.

The operating system also maintains other information needed to manage the thread and its relationship with the process.

A process can contain multiple threads. Each thread has its own execution context, while the threads generally share the process's address space and other process-level resources.

What Happens During a Context Switch?

When the operating system switches the CPU from one thread to another, it must preserve the outgoing thread's necessary execution state and restore the incoming thread's saved state.

This allows the incoming thread to continue from its own previous execution point.

A context switch can happen in two important situations:

  • Between threads of the same process: The CPU switches execution from one thread to another, while both threads continue using the same process address space.
  • Between threads of different processes: The CPU switches execution to a thread belonging to another process. This may also involve changing the active address space and associated memory-management context.

Why Is Execution Context Important?

  • It allows a thread to resume correctly.
  • It preserves individual execution progress.
  • It supports switching between threads.
  • It allows multiple threads to share CPU time.
  • It helps the operating system coordinate processor use.

Technical Distinction

A process and a thread are not the same thing.

The process provides the resource-owning environment. The thread provides an individual path of execution within that environment.

The execution context primarily describes the thread's current processor state, rather than a single shared set of CPU register values for the entire process.

5.8 Process Address Space

A process also has an associated address space. This is the range of memory addresses that the process can use, subject to the operating system's memory protection and management rules.

In modern operating systems, a process commonly uses a virtual address space. Virtual addresses are translated by the system's memory-management hardware and operating-system mechanisms into locations in physical memory.

This arrangement helps provide memory protection and gives each process its own organised view of memory.

Threads belonging to the same process generally share that process's address space. This allows them to access shared program code and process data.

Important Distinction

Threads in the same process generally share the process's address space, but each thread has its own execution context and its own stack.

Shared memory does not mean that every part of a thread's execution state is shared with other threads.

5.9 Common Regions of a Process Address Space

A typical process address space can contain several logical regions. Their exact arrangement depends on the operating system, architecture, and program.

  • Text / Code segment: Contains the program's executable instructions.
  • Data segment: Contains global and static variables that have been initialised.
  • BSS segment: Contains global and static variables that are uninitialised or initially zero-initialised.
  • Heap: Provides memory used for dynamic allocation while the program runs.
  • Stack: Supports function calls, local variables, return information, and other call-related data.

Important Memory Concept

The heap and stack are different memory regions with different purposes.

The heap is commonly used for dynamically allocated memory. The stack supports function-call execution and related local data.

Each thread generally has its own stack, while threads belonging to the same process share the process's heap and other shared address-space regions.

These are logical regions of a process's address space. They should not be confused with separate physical memory chips.

5.10 Understanding the Process Memory Layout

The following is a simplified conceptual view of common regions in a process's virtual address space. It is not a universal physical memory arrangement.

Higher Address Region

Stack

Function calls and local data.

Dynamic Memory Region

Heap

Dynamically allocated memory.

Initialised Data Region

Uninitialised Data Region

The arrangement above is a teaching representation. Actual address-space layouts can differ, and additional regions such as shared libraries, memory-mapped files, and other mappings may also be present.

5.11 How Do the PCB and Process Memory Work Together?

The PCB and the process address space serve different but related purposes.

  • The PCB contains operating-system management information about the process.
  • The process address space provides the process with its organised view of memory.
  • Memory-management information helps the operating system and hardware manage and protect that address space.
  • Thread-management information preserves the execution state needed to resume individual threads.
  • Threads belonging to the same process generally share the process's address space and process-level resources.

Together, these mechanisms allow the operating system to manage a process and its threads as they execute, wait, resume, and eventually terminate.

Technical Summary

A process is an executing instance of a program with an associated address space, execution state, and operating-system-managed resources.

The PCB stores process-level management information. The PID identifies the process. Each thread has its own execution context, including its program counter and saved CPU registers. The process address space organises the memory available to the process and is generally shared by its threads.

6. Components and Architecture

A process is not simply a program running on a computer. The operating system must maintain information about the process so that it can identify it, manage its execution, and coordinate its use of resources.

6.1 How Does the Operating System Manage a Process?

Imagine a computer running a web browser, a music player, and a file manager at the same time.

The operating system must distinguish these processes and keep track of their individual execution states, CPU requirements, memory information, and resources.

To do this, the operating system maintains management information associated with each process.

Central Concept: Process Control Block (PCB)

A Process Control Block (PCB) is an operating-system data structure that contains information used to manage a particular process.

Think of it as the operating system's management record for that process.

6.2 Why Does the Operating System Need a PCB?

Without process-management information, the operating system would have difficulty keeping track of individual processes and managing their execution.

The PCB helps the operating system maintain information needed for tasks such as:

  • Identifying a particular process.
  • Tracking whether the process is ready, running, or waiting.
  • Preserving processor execution information.
  • Managing CPU scheduling information.
  • Keeping track of memory-management information.
  • Managing associated input/output and other resources.

  • The operating system uses the PID to distinguish processes.
  • System tools can display a process using its PID.
  • A PID may be reused after a process terminates.

6.4 How Do These Components Work Together?

The information associated with a process serves different purposes, but the operating system uses it together to manage execution.

Identity and State

The PID identifies the process, while its state describes its current execution situation.

Processor Execution

The program counter and saved CPU register information help preserve the execution context.

CPU Scheduling

Scheduling information helps the operating system decide when a process should receive CPU time.

Memory Management

Memory-management information helps the operating system manage the process's address space.

Input/Output and Accounting

6.5 Is the PCB the Same as the Process's Memory?

No. The PCB and the process address space are related to process management, but they are different things.

  • PCB: Contains operating-system management information about the process.
  • Process address space: Provides the process with its organised view of memory.
  • CPU registers: Are hardware storage locations inside the processor.

Important Technical Distinction

The PCB is not the process's entire memory, and it is not the CPU itself.

Some PCB information may refer to other structures or resources used to manage the process. This does not mean that all of those structures are physically stored inside the PCB.

The operating system maintains information about each process so that it can identify the process, track its state, preserve execution information, and manage its resource requirements.

7. How Does a Process Work? The Complete Working Mechanism

A process does not simply appear and immediately use the CPU. It moves through a series of stages during its lifetime. The operating system manages these stages so that multiple processes can share the computer's resources in an organised way.

In this section, we will follow a process from the moment it is created until it finishes its work.

7.1 Understanding the Process Lifecycle

The process lifecycle describes the different states a process can enter while it exists in an operating system. A process may be waiting for the CPU, actively executing instructions, waiting for an event, or finishing its execution.

To understand this lifecycle, imagine opening a web browser. The operating system must create a process, prepare it for execution, give it CPU time, manage its waiting periods, and eventually clean up when the process finishes.

Important idea: A process changes states during its lifetime. The operating system keeps track of these changes and decides when a process can use the CPU.

7.2 The Five Basic States of a Process

A commonly taught operating-system model describes a process using five basic states.

  1. New: The process is being created by the operating system.
  2. Ready: The process is prepared to execute and is waiting for CPU time.
  3. Running: The process is currently executing instructions on a CPU.
  4. Waiting (Blocked): The process cannot continue until a required event occurs, such as completion of an input/output operation.
  5. Terminated: The process has finished or has been stopped.
Remember: Ready means waiting for the CPU. Waiting means waiting for an event or operation to complete. These two states are not the same.

7.3 Stage 1: Process Creation

Every process begins its life when the operating system creates it. This may happen because a user opens an application or because another process requests the creation of a new process.

For example, when you open a web browser, the operating system receives a request to start the application.

During process creation, the operating system performs the necessary setup. Depending on the operating system and the application, this may include:

  • Preparing the program's execution environment.
  • Establishing the process's memory address space.
  • Creating the required process-management information.
  • Assigning a process identifier (PID).
  • Setting up the resources needed to begin execution.

Once the necessary preparation is complete, the process can move into the Ready state.

Key point: A program stored on a storage device is not automatically a running process. The operating system must create and prepare a process before its instructions can execute.

7.4 Stage 2: Entering the Ready State

A Ready process has been prepared to execute and is waiting for CPU time. It is not currently using the CPU. It may still request additional resources while it runs.

The operating system keeps track of processes that are ready to execute. These processes are commonly organised in a ready queue.

Imagine that three applications are ready to run:

  • Process A: A web browser.
  • Process B: A music player.
  • Process C: A file manager.

All three processes may be ready to execute, but they may have to wait for the CPU to become available.

Important distinction: A Ready process is waiting for CPU time. It is not waiting for a disk operation, network response, or user input.

7.5 Stage 3: CPU Scheduling and Dispatch

When the CPU is available, the operating system must decide which ready process should execute next.

This decision is made by the CPU scheduler. It selects a process from the ready queue according to the scheduling policy being used.

After a process has been selected, the dispatcher gives that process control of the CPU. This involves carrying out the necessary steps to begin or resume its execution.

CPU Scheduler vs Dispatcher

CPU Scheduler: Decides which ready process should run next.

Dispatcher: Transfers CPU control to the process selected by the scheduler.

Once the process receives the CPU, it moves from the Ready state to the Running state.

7.6 Stage 4: Process Execution

A process enters the Running state when its instructions are being executed by the CPU.

During execution, the CPU works with information associated with the process. This includes its instructions, memory, and execution state.

The process may perform different kinds of work, such as:

  • Performing calculations.
  • Reading or changing data in memory.
  • Requesting information from a storage device.
  • Communicating over a network.
  • Responding to user input.

While running, a process may reach one of several outcomes:

  • It may continue executing its instructions.
  • It may be moved back to the Ready state.
  • It may enter the Waiting state.
  • It may finish and enter the Terminated state.
Key point: Running means the process is currently executing on a CPU. It does not mean the process will remain on the CPU continuously until it finishes.

7.7 Stage 5: Entering the Waiting (Blocked) State

Sometimes a running process needs something that is not immediately available. It may need to wait for an operation or event to complete.

For example, a process may need to:

  • Read data from a storage device.
  • Receive information from a network.
  • Wait for a user to press a key.
  • Wait for a required event or resource.

While the required operation is pending, the process cannot continue with the instruction that depends on that operation. It therefore enters the Waiting, or Blocked, state.

The operating system can use the CPU to execute another ready process instead of leaving the CPU idle.

Ready vs Waiting

Ready: The process is able to execute but is waiting for CPU time.

Waiting: The process cannot continue until a required event or operation is completed.

7.8 Stage 6: Context Switching

A CPU may switch from executing one process to executing another. This change is called a context switch.

To understand why this is necessary, imagine that Process A is running and the operating system decides that Process B should execute next.

The operating system must preserve the execution information needed by Process A so that it can continue later. It then restores the relevant execution information for Process B.

In a simplified explanation, the steps are:

  1. Process A is currently running.
  2. The operating system interrupts or pauses its execution.
  3. The relevant execution state of Process A is saved.
  4. The relevant execution state of Process B is restored.
  5. Process B begins or resumes execution.
Important: A context switch is an operation performed by the operating system. It is not one of the five basic process states.

7.9 Stage 7: Returning from Waiting to Ready

A process does not remain in the Waiting state forever. When the event or operation it was waiting for is completed, it can become eligible to execute again.

For example, suppose a process was waiting for data from a storage device. When the required data becomes available, the operating system can move the process from Waiting to Ready.

The general sequence is:

  1. The required operation or event is completed.
  2. The process leaves the Waiting state.
  3. The process enters the Ready state.
  4. The CPU scheduler may select it later.
  5. The process returns to the Running state when dispatched.
Remember: A process becoming Ready does not mean it immediately receives the CPU. It must still wait for the scheduler to select it.

7.10 Stage 8: Process Termination

A process eventually reaches the end of its lifetime. This happens when it completes its work or when it is stopped by the operating system or another authorised request.

When a process terminates, the operating system performs the necessary cleanup. Depending on the operating system and the circumstances, this may include:

  • Recording the process's completion status.
  • Releasing resources that are no longer needed.
  • Cleaning up process-management information.
  • Making memory and other resources available for reuse.

The process then enters the Terminated state.

Key point: Termination marks the end of the process's execution lifecycle. The operating system may still need to complete cleanup and record information about its termination.

7.11 Putting Everything Together: A Web Browser Example

Imagine opening a web browser, visiting a website, waiting for its content to load, and then closing the application. We can use this example to understand how a process moves through its lifecycle.

  1. New: You open the browser, and the operating system creates the required process.
  2. Ready: The process has been prepared and waits for CPU time.
  3. Running: The CPU executes the browser process's instructions.
  4. Waiting: The process may need to wait for a network response or another required operation.
  5. Ready again: When the required event completes, the process can return to the Ready state.
  6. Running again: The scheduler may select the process so it can continue.
  7. Terminated: When the process finishes or is closed, it eventually reaches termination.
A note about real browsers: Modern browsers may use multiple processes and threads for different tasks. This example follows one simplified process to make the basic lifecycle easier to understand.

7.12 Understanding the Main State Transitions

A process moves between states when particular events occur. In the basic five-state model, the main transitions are:

  • New → Ready: The operating system has completed the necessary preparation for the process.
  • Ready → Running: The scheduler selects the process and the dispatcher gives it CPU control.
  • Running → Ready: The process is moved off the CPU, for example when its time slice expires or it is preempted.
  • Running → Waiting: The process must wait for an event or operation.
  • Waiting → Ready: The event or operation the process was waiting for has completed.
  • Running → Terminated: The process completes or is stopped.
Model limitation: The five-state model is a simplified teaching model. Real operating systems may use additional states and more detailed rules for process management.

7.13 Section Summary

A process moves through a managed lifecycle. The operating system creates it, prepares it for execution, schedules it for CPU time, manages periods when it must wait, and handles its termination.

The five basic states help us understand this lifecycle: New, Ready, Running, Waiting, and Terminated.

Scheduling determines which ready process should execute. Context switching allows the CPU to move between processes. When a waiting event completes, a process can return to Ready and compete for CPU time again.

  • Identify the five basic states of a process.
  • Explain how a process is created.
  • Distinguish between Ready and Waiting.
  • Explain the roles of the CPU scheduler and dispatcher.
  • Describe what happens during process execution.
  • Explain why context switching is necessary.
  • Describe how a waiting process returns to Ready.
  • Explain how a process reaches termination.
  • Trace a process through its basic lifecycle.

10.1 A Real-Life Scenario: Opening a Text Editor

Imagine Alex opens a text editor to write a document. The application may look like one simple window, but behind that window the operating system is managing a process and coordinating its use of computer resources.

10.2 Follow the Process Through Its Lifetime

  1. Alex opens the text editor — New.

    The operating system begins creating a process for the application. The process starts in the New state while the operating system prepares the information and resources needed for execution.

  2. The process becomes Ready.

    The process has been prepared for execution. It enters the Ready state and waits for the CPU scheduler to select it.

  3. The process starts Running.

    The scheduler selects the process. The dispatcher performs the necessary context switch and transfers CPU control to it. The text editor begins executing its instructions.

  4. Alex opens an existing document — Waiting.

  6. The I/O operation completes — Ready.

  7. The process runs again — Running.

    The process does not immediately receive the CPU just because its I/O operation has completed. It must wait until the scheduler selects it again. The dispatcher then restores the necessary execution context, allowing the text editor to continue.

  8. Alex closes the application — Terminated.

    When the application exits, its process enters the Terminated state. The operating system performs the necessary cleanup and releases resources that are no longer needed.

11. Common Mistakes and Misconceptions

When learning about processes, it is easy to confuse related concepts or make assumptions about how the operating system works.

Let's examine ten common misconceptions and understand what actually happens inside an operating system.

11.1 Ten Common Process Misconceptions

11.1.1 Program and Process Are the Same

Common misconception: A program and a process are exactly the same thing.

Correct understanding: A program is a set of instructions stored as a file. A process is an instance of a program in execution, together with its execution state and associated resources.

Example: A text editor stored on your device is a program. When you open it, the operating system creates a process to execute it.

11.1.2 Every Process Is Always Running

Common misconception: Every process is constantly using the CPU.

Correct understanding: A process can be New, Ready, Running, Waiting, or Terminated. In the basic process-state model, Running means the process is currently executing on a CPU.

Example: A music application waiting for data from storage may be in the Waiting state rather than executing instructions on the CPU.

11.1.3 Ready and Waiting Mean the Same Thing

Common misconception: Ready and Waiting both mean that a process is waiting, so they are identical.

Correct understanding: Ready means the process is prepared to execute but is waiting for CPU time. Waiting means the process cannot continue until a particular event or operation is completed.

Example: A process in the Ready queue needs CPU time. A process waiting for a file-reading operation needs that operation to complete.

11.1.4 A Ready Process Immediately Gets the CPU

Common misconception: As soon as a process enters Ready, it starts executing.

Correct understanding: A Ready process must wait until the CPU scheduler selects it. The dispatcher then transfers CPU control to the selected process.

Example: Several processes may be Ready simultaneously. On a single CPU core, only one process thread can execute on that core at a time.

11.1.5 Scheduler and Dispatcher Are the Same

Common misconception: The CPU scheduler and dispatcher perform exactly the same job.

Correct understanding: The scheduler selects which Ready process should execute next. The dispatcher transfers CPU control to the selected process and performs the necessary context-switching work.

Example: The scheduler chooses the next process. The dispatcher helps the CPU begin executing it.

11.1.6 Context Switching Is Simply Executing Another Process

Common misconception: A context switch is simply the execution of another process.

Correct understanding: A context switch involves saving the execution context of one process or thread and restoring the context of another.

Example: The operating system saves the necessary execution information of the current process before transferring CPU control to another process.

11.1.7 A Waiting Process Continues Using the CPU

Common misconception: A process waiting for I/O continues consuming CPU time while it waits.

Correct understanding: A blocked process generally does not execute instructions on the CPU while waiting for the required event. The CPU can execute another Ready process.

Example: While one process waits for a storage operation, another Ready process can use the CPU.

11.1.8 Every Application Has Only One Process

Common misconception: One application always corresponds to exactly one process.

Correct understanding: An application may use multiple processes, and a single process may contain multiple threads. The relationship depends on the application's design and the operating system.

Example: A modern web browser may use separate processes for tasks such as rendering pages and handling other browser services.

11.1.9 A Terminated Process Is Temporarily Inactive

Common misconception: A terminated process is simply a process that is temporarily inactive.

Correct understanding: A terminated process has finished execution or has been stopped. The same process instance does not return to Ready or Running. The operating system handles its remaining cleanup.

Example: When a text editor process exits, it no longer continues executing as that process.

11.1.10 Every Process Follows One Fixed Lifecycle

Common misconception: Every process must follow exactly the same sequence of state transitions.

Correct understanding: A process can move repeatedly between Ready, Running, and Waiting. Its actual journey depends on scheduling decisions, I/O requests, events, and how execution ends.

Example: A process may run, wait for I/O, return to Ready, run again, and repeat this cycle many times before termination.

11.2 Quick Comparison — Remember the Differences

These related concepts are easy to confuse. Use this table to remember their essential differences.

Concepts Remember the Difference
Program vs. Process Stored instructions vs. executing instance.
Ready vs. Waiting Waiting for CPU time vs. waiting for an event.
Scheduler vs. Dispatcher Selects the process vs. transfers CPU control.
Running vs. Terminated Currently executing vs. execution has ended.
Process vs. Thread Resource-owning execution environment vs. execution unit.

11.3 Key Takeaway

A process is not simply a program that is open on the screen. It is an executing entity managed by the operating system.

Understanding process states, scheduling, context switching, resource usage, and the process lifecycle helps explain how an operating system coordinates multiple activities on a computer.

12. Advantages and Limitations of Processes

Understanding the Trade-Off

Processes make multitasking, isolation, resource management, and responsive computing possible. However, creating and managing processes also requires memory, CPU time, and coordination.

Understanding both sides helps us see why processes are essential to modern operating systems and why they must be managed carefully.

12.1 Advantages of Processes

Processes provide several important benefits that help an operating system manage running applications.

1. Multitasking

How it helps:

  • Allows multiple applications to execute during overlapping periods.
  • The operating system schedules CPU time among processes.
  • Multiple processes can execute simultaneously on different CPU cores.

Example: Listening to music while browsing the internet.

2. Process Isolation

How it helps:

  • Processes generally have separate virtual address spaces.
  • Memory protection helps prevent unauthorized access between processes.
  • Problems in one process are less likely to directly affect another.

Example: A crash in a text editor does not necessarily crash a music player.

3. Better Resource Management

How it helps:

  • The operating system manages CPU allocation.
  • It coordinates memory and I/O resource usage.
  • It manages competing requests from different processes.

Example: The scheduler selects which ready process receives CPU time.

4. Improved Responsiveness

How it helps:

  • A process waiting for blocking I/O can enter the Waiting state.
  • The CPU can then execute another ready process.
  • This helps the system remain productive while operations are pending.

Example: A browser waiting for a file operation while another application continues running.

5. Controlled Execution

How it helps:

  • Every process has an identifiable lifecycle.
  • The operating system tracks process states.
  • It can create, schedule, suspend, resume, and terminate processes.

Example: The operating system can terminate an unresponsive application.

12.2 Limitations and Challenges of Processes

Although processes provide important benefits, managing them introduces costs and technical challenges.

1. Process Creation Overhead

Why it is a limitation:

  • Creating a process requires operating-system operations.
  • The OS establishes process-management structures and resources.
  • Creation consumes time and memory.

Example: Starting a new application requires more work than simply continuing an existing process.

2. Context-Switching Overhead

Why it is a limitation:

  • The OS saves the current process's execution context.
  • It restores the context of another process.
  • This switching consumes CPU time without directly advancing either application's work.

Example: Frequent switching between processes can add unnecessary overhead.

3. Memory Consumption

Why it is a limitation:

  • Processes require memory for execution and management.
  • Multiple processes can increase total memory demand.
  • Some memory may be shared, so the cost is not always fully duplicated.

Example: Opening many memory-intensive applications can put pressure on available RAM.

4. Inter-Process Communication Complexity

Why it is a limitation:

  • Processes sometimes need to exchange information.
  • Communication requires mechanisms such as pipes, sockets, or shared memory.
  • Designing and managing communication can be complicated.

Example: Two separate applications exchanging information through a communication channel.

5. Synchronization Problems

Why it is a limitation:

  • Processes may access shared resources.
  • Poor coordination can produce race conditions.
  • Incorrect resource coordination can also lead to deadlocks.

Example: Two processes attempting to update the same shared data at the same time.

6. Resource Contention

Why it is a limitation:

  • Processes compete for limited resources.
  • CPU time, memory, storage, and I/O devices may become bottlenecks.
  • Heavy competition can reduce overall system performance.

Example: Several demanding applications competing for CPU time.

12.3 Advantages vs Limitations — Quick Comparison

The following table summarises the benefits processes provide and the costs or challenges associated with managing them.

Advantages Limitations
Supports multitasking Requires management overhead
Provides memory isolation Requires memory resources
Improves responsiveness Context switching consumes CPU time
Enables resource management Processes compete for resources
Supports controlled execution Communication and synchronization add complexity

12.4 Important Takeaway

Processes provide the operating system with a structured way to manage running programs. They support multitasking, protection, resource management, and responsiveness.

However, these benefits come with costs: process creation, memory consumption, context switching, communication, synchronization, and resource competition.

The central lesson: Processes make modern multitasking systems possible, but effective process management requires balancing their benefits against their overhead.

13. Connections to Other Operating-System Concepts

Understanding the Connections

A process does not operate in isolation. It interacts with several other operating-system concepts and mechanisms that work together to make a computer function.

Understanding these connections helps us see how the different parts of an operating system cooperate.

13.1 Process and Program

The Relationship

  • A program is a passive set of instructions stored on a device.
  • A process is an instance of a program in execution.
  • One program can have multiple running process instances.
  • Each process has its own execution state and resources.

Analogy: A recipe is a program; someone actively following that recipe is like a process.

Example: Opening two instances of the same application can create two separate processes.

13.2 Process and Thread

The Relationship

  • A process provides an environment in which threads execute.
  • A thread is an individual path of execution within a process.
  • Multiple threads can belong to one process.
  • Threads in the same process share resources such as its address space and open files.
  • Each thread maintains its own execution context, including its registers and stack.

Analogy: A process is a workshop; threads are workers operating within that workshop. They share the workshop's facilities but perform their own tasks.

Example: A browser may use different threads for interface operations, networking, and other activities.

13.3 Process and Process Control Block (PCB)

The Relationship

  • The operating system maintains information about every process.
  • This information is organised in a Process Control Block (PCB).
  • The PCB contains information such as process ID, state, scheduling information, and saved execution context.
  • The operating system uses this information to manage processes.

Analogy: A PCB is like an employee's official record containing information needed to manage their work.

Example: During a context switch, the OS saves and restores relevant process execution information.

13.4 Process and CPU Scheduling

The Relationship

  • Multiple processes may compete for CPU time.
  • The scheduler selects a process from the Ready state.
  • The dispatcher performs the handover of CPU control to the selected process.
  • Scheduling policies determine how CPU time is distributed.

Analogy: The scheduler is like a manager deciding who gets to use a shared machine next.

Example: While one process waits for I/O, the scheduler can select another ready process.

13.5 Process and Memory Management

The Relationship

  • Each process generally has its own virtual address space.
  • Virtual addresses are translated into physical addresses.
  • Hardware mechanisms, such as the memory management unit (MMU), cooperate with OS-managed memory structures to perform address translation.
  • Memory protection helps isolate processes.
  • Physical memory is allocated and managed as processes execute.

Analogy: Each process has its own numbered map of a building. The memory-management system translates those numbers into actual physical rooms.

Example: Two processes can use the same virtual address without necessarily accessing the same physical memory location.

13.6 Process and Interrupts

The Relationship

  • Interrupts notify the CPU that an event requires attention.
  • Hardware devices can generate interrupts to signal events such as I/O completion.
  • The operating system handles the event.
  • The OS may then update a process's state if the event satisfies the condition it was waiting for.
  • An interrupt does not automatically make a process Ready; the appropriate state transition depends on the event and process conditions.

Analogy: An interrupt is like a doorbell notifying someone that something requires attention. The notification itself does not determine what happens next.

Example: An I/O completion interrupt may allow a process waiting for that operation to return to the Ready state.

13.7 Process and Inter-Process Communication (IPC)

The Relationship

  • Separate processes sometimes need to exchange information.
  • Inter-Process Communication (IPC) provides mechanisms for this exchange.
  • Common mechanisms include pipes, sockets, message queues, and shared memory.
  • Synchronization may be necessary when processes access shared information.

Analogy: Two separate offices communicating through a telephone, message service, or shared noticeboard.

Example: A client application communicates with a separate server process through a network socket.

13.8 Process and File System

The Relationship

  • Processes often need to create, open, read, write, and close files.
  • The operating system provides file-system services.
  • Processes request these services through system calls.
  • The OS enforces applicable file permissions and access controls.

Analogy: A process is like an employee requesting access to documents from a records department.

Example: A text editor requests that the OS open and read a document.

13.9 Process and System Calls

The Relationship

  • A running program requests operating-system services through system calls.
  • System calls provide a controlled interface to kernel services.
  • Requests may involve file operations, process creation, memory management, and I/O.
  • The kernel handles these requests according to operating-system rules.

Analogy: A system call is like submitting an official service request to an organisation's central administration.

Example: A program requests the operating system to create another process.

13.10 Bringing Everything Together — The Big Picture

The concepts above are connected. They cooperate to make process execution possible.

13.11 Important Takeaway

A process is not an isolated operating-system object. It is connected to CPU scheduling, memory management, threads, interrupts, system calls, files, and communication mechanisms.

Each of these concepts contributes to the overall operation of the system.

The central lesson: Understanding processes becomes much easier when we understand how they interact with the other components of an operating system.

15. Quick Revision and Key Takeaways

Bringing Everything Together

You have explored processes, their lifecycle, internal structure, management, scheduling and relationships with other operating-system concepts.

This final section brings the essential ideas together. Use it to revise important terminology, connect related concepts and check your understanding of process management.

15.1 Process at a Glance

A process is a program in execution. It is an active instance of a program, with its own address space, execution resources and one or more threads.

Remember:

  • A program is passive; a process is active.
  • A process has its own address space and managed resources.
  • A process contains one or more threads of execution.
  • Each thread has its own execution context and stack.
  • The operating system manages processes and their resources.
  • Multiple processes can make progress concurrently.
  • Multiple threads may execute in parallel on different CPU cores.

15.2 Essential Terminology

  • Program: A stored set of instructions that can be executed.
  • Process: An executing instance of a program, with its associated execution environment and resources.
  • Process ID (PID): An identifier assigned to a process by the operating system.
  • Process Control Block (PCB): An operating-system data structure containing information needed to manage a process.
  • Thread: An execution unit within a process.
  • Context Switch: The operation of saving one execution context and restoring another so that a different process or thread can execute.
  • Scheduler: The operating-system component that selects an eligible process or thread for CPU execution.
  • Dispatcher: The component that transfers CPU control to the selected execution unit.
  • Inter-Process Communication (IPC): Mechanisms that allow processes to exchange information and coordinate their activities.
  • Program Counter (PC): A register in a thread's execution context that holds the address of its next instruction.

15.3 Process Lifecycle Revision

A process moves through different states during its lifetime. The operating system tracks these states to manage execution.

  • New: The process is being created.
  • Ready: The process is prepared to execute and is waiting for CPU allocation.
  • Running: A thread belonging to the process is currently executing on a CPU.
  • Waiting (Blocked): The process cannot continue until a required event occurs, such as completion of an I/O operation.
  • Terminated: The process has finished or has been stopped.

Important State Transitions

  • New → Ready: The process is admitted into the ready state.
  • Ready → Running: The dispatcher gives the selected process CPU time.
  • Running → Ready: The running process is pre-empted or its allocated time slice expires.
  • Running → Waiting: The process must wait for an event or operation, such as an I/O request, to complete.
  • Waiting → Ready: The required event occurs and the process becomes eligible for CPU scheduling again.
  • Running → Terminated: The process finishes or is terminated.

Key distinction: A process in the Ready state is waiting for CPU time. A process in the Waiting state is waiting for an event.

15.4 How the Operating System Manages Processes

  1. Process Creation: The operating system creates a process and establishes the address space and resources required for its execution.
  2. Process Tracking: The operating system maintains process information, including its state, identifier and management data.
  3. CPU Scheduling: The scheduler selects an eligible process or thread for execution.
  4. Context Switching: The operating system saves the execution context of one process or thread and restores another.
  5. Memory Management: The operating system manages process address spaces, memory allocation and protection, with hardware support such as the Memory Management Unit (MMU).
  6. Communication: Processes exchange information using IPC mechanisms such as pipes, message queues, sockets and shared memory.
  7. Process Termination: The operating system performs the necessary cleanup and releases resources associated with the process.

15.5 Important Comparisons to Remember

Program vs Process

  • Program: Stored instructions.
  • Process: An executing instance of a program.

Process vs Thread

  • Process: An executing program with its own address space and managed resources.
  • Thread: An execution unit within a process.
  • Threads in the same process share its address space and many process resources.
  • Each thread has its own execution context, including its registers and stack.

Ready vs Waiting

  • Ready: Waiting for CPU allocation.
  • Waiting: Waiting for an event or operation to complete.

Scheduler vs Dispatcher

  • Scheduler: Selects the next eligible execution unit.
  • Dispatcher: Transfers CPU control to the selected unit.

Program Counter vs Process ID

  • Program Counter: Holds the address of the next instruction for a particular thread.
  • Process ID: Identifies a process within the operating system.

15.6 Connections to Other Operating-System Concepts

  • Memory Management: Provides processes with managed address spaces and memory protection.
  • CPU Scheduling: Determines which eligible process or thread receives CPU time.
  • Interrupts: Allow the processor to respond to events, including hardware events.
  • System Calls: Provide a controlled interface through which programs request operating-system services.
  • File System: Provides mechanisms for storing, accessing and managing files.
  • IPC: Enables processes to communicate and coordinate.
  • Synchronization: Helps coordinate access to shared resources and prevent problems such as race conditions.

15.7 Common Misconceptions to Avoid

  • A program and a process are not the same thing.
  • A Ready process is not currently executing.
  • A Waiting process is not simply waiting for CPU time.
  • A process and a thread are not interchangeable terms.
  • A context switch does not mean that a process has terminated.
  • Concurrency does not always mean that multiple tasks execute at the exact same instant.
  • Processes do not automatically share all their memory with one another.
  • An interrupt does not automatically mean that the interrupted process will immediately run again.
  • A process can contain multiple threads, and a thread is the unit of execution scheduled on a CPU.

15.9 The Big Picture: Why Processes Matter

A computer runs many programs and performs many activities. The operating system needs a way to organise, track, schedule and control their execution.

Processes provide an important abstraction for this work. They allow the operating system to manage executing programs, coordinate their access to resources, protect their memory and support communication between them.

Final takeaway: Process management is one of the central responsibilities of an operating system. It helps turn a collection of competing programs into an organised and manageable computing environment.
